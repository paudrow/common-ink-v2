# Purging takes a deleted note's text out of history

ADR 0002 makes history the source of truth: nothing is lost, and every change can be undone. Trash builds on that, since a deleted note is a delete change that restoring undoes. But sometimes a note must really be gone: a password pasted by mistake, or a note kept past the time anyone wants it. So one change is allowed to remove history: a **purge**.

A purge takes one note in Trash, named by its delete. Every change belongs to a note, decided when the change is written and never after: a change to a file that's there is that file's note's; one that makes a file carries on the note of the change it brings back (an undo, Restore, a restore to an older version), unless that note is a file somewhere else; any other change starts a note. So a note restored beside a new one at its path, as "Plan (restored).md", is the same note, and a note restored and deleted again is purged whole, at every path it had. What a purge removes is one note's changes, and nothing written or purged later can change which those are. In each path's history, one change takes their place. It has no text and no diff, can't be undone, and says who purged the note and when. A note's changes at a path go from no file to no file, so every other note's history, at the same path too (a daily note, Untitled N), replays exactly as before. A property test checks that, with purges at any point, against a model of which note each change belongs to, and that no purge brings another delete back into Trash.

- **History from before note ids is given them once, with care.** A workspace's older changes get their notes from history by the same rule when it first opens, reading each change once without its text (about 2.5 s for a million changes; the Durable Object's 30 s of CPU would allow some ten million). History doesn't say when a deleted file was restored to an older version, so a new file whose text is exactly the text a note deleted at its path had when deleted is taken for that note brought back, if it says more than a heading: a daily note made again from its template is a new note. That's a guess, so a note carried on by it is kept from Trash retention's automatic purge, and so is a note deleted at a path where a new file wasn't taken for it, in case that file was it restored to some other version. Such notes stay in Trash, marked Kept and saying why, however old, until a person deletes them forever. A property test checks that, after the backfill, retention purges nothing that live writes wouldn't have.
- **Delete forever says all it takes.** A note can have earlier parts, each ended by a delete: restored and deleted again, or taken by the backfill for a later file. Trash lists those with other text than the note's, and the confirmation for Delete forever, or Empty Trash, names each one's path and words.
- **Only notes in Trash.** A note that's there can't be purged. Delete it first, so it passes through Trash.
- **Only a person.** Purge is an operation of the app's, not offered over MCP, and refused for agents and extensions, whatever route they use. The app asks first, for one note (Delete forever) or all of them (Empty Trash). An empty agent header counts as an agent, never as the person.
- **Or Trash retention.** Once a day the workspace's Durable Object purges notes deleted more than `trash.retentionDays` days ago (30 by default). Those changes are by Trash retention, so History says so. Only a person may change `trash.retentionDays`, and retention uses the value a person last set, whatever wrote the settings file since, so no agent can make Trash retention purge sooner.
- **Edits can't bring it back.** The ids of edits to a purged note stay, with their text's hash taken out, so a page that never heard an answer and sends an edit again is refused. A write based on a purged revision can't be merged, so it's refused too.
- **The search index forgets.** A purged note's rows leave the index at once, so search can't find it. Its words stay in the index's blocks until they're merged, which rewrites the whole index (about 2 s at 30,000 notes), so the workspace's alarm does it 30 seconds after a purge, once for any number of them, and the daily retention purge merges as it ends.
- **Browsers forget, but not what you typed offline.** A page that hears of a purge drops the note's kept copy, its draft and any edit held for it, and closes it where it's open. A page's kept copies of files the workspace no longer lists go when it next lists them. A device that was offline when the note was purged doesn't hear of it. What you typed there stays: sent once it's back, the edit is refused, and the page keeps it as a conflict, text and all, so you can save it as a new note. Throwing away typing nobody has seen was the worse choice.

## Consequences

- Undo can't reach a purge, and Restore can't bring a purged note back. That's the point.
- Labels and other workspace JSON that name a purged path keep the name. The text they pointed to is gone, so a label's version can't be opened.
- Purge doesn't promise more than storage does. SQLite may keep freed pages' old bytes in the database file until they're reused, and Durable Objects' point-in-time recovery keeps the database as it was, purged text included, for up to 30 days.
- Uploads that only the purged note used stay: their bytes in R2 and their entries in `.common-ink/uploads.json`. Purging uploads too is follow-up work.
